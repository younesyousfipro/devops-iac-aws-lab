# Decisions

DevOps decisions for this repository, recorded when they are made. The starting point is the OpenClassrooms starter kit (first commit), adapted to production-like practices.

## Hosting and repository (2026-11-09)

| Decision | Rejected | Reason |
|---|---|---|
| AWS for the three exercises (revised: AWS for Ex1 only; Ex2 on 2026-11-13 and Ex3 on 2026-11-14 run locally, see their sections) | local Docker option; Azure | the starter kit covers AWS for all three exercises (managed OpenSearch for Ex2); the Ex1 Docker option boots a QEMU VM that needs `/dev/kvm`, not available on macOS; Azure only appears in the Ex3 title, with no starter files and no managed OpenSearch equivalent. Consequence: real costs, covered by the AWS Free plan credits; every session ends with `terraform destroy` |
| One repository, one folder per exercise (`01-provision-configure`, `02-observability-elk`, `03-load-balancing`) | one repository per exercise | the brief asks for one repository; the exercises are small; each folder has its own Terraform state, so nothing is shared |
| Hosted on GitHub as `devops-iac-aws-lab` | GitLab (named in the brief) | GitHub is the author's main platform; the Ex1 deliverable asks for a GitHub link; the deliverables are also uploaded as a zip |
| Starter kit history kept (initial commit), `origin` changed | fresh `git init` | the diff between the starter kit and this work stays visible, and the kit stays credited |
| Repository docs in English | French | readable by anyone reviewing the repository |

## Terraform foundations (2026-11-09)

| Decision | Rejected | Reason |
|---|---|---|
| Remote state in S3, native locking (`use_lockfile = true`) | local state; DynamoDB locking | the state survives the laptop and is locked during an apply; native S3 locking (Terraform 1.10+) replaces DynamoDB, now deprecated |
| State bucket created by a separate `00-bootstrap/` folder, with local state | bucket created by hand in the console | the bucket is code too; its own state holds nothing sensitive. Consequence: the bucket is not destroyed at the end of a session (cost: a few cents at most) |
| Existing public key registered with `aws_key_pair` (dedicated `id_ed25519_aws`) | key generated by Terraform (`tls_private_key`, starter kit) | a generated private key is stored in clear in the state; with an existing key, the private key never leaves the laptop |
| Production-like hygiene: SSH open to the author's IP only, pinned recent provider versions, AMI looked up by a data source | starter kit defaults (`0.0.0.0/0`, provider `~> 4.16`, hard-coded AMI) | least privilege; reproducible versions; an AMI ID gets outdated and differs by region |
| Default VPC | custom VPC with private subnets | private subnets need a NAT gateway, which is billed per hour; high availability is out of scope for these exercises |

## AWS account (2026-11-09)

| Decision | Rejected | Reason |
|---|---|---|
| Keep the account created with "Sign up for AWS (new)": one project `devops-iac-aws-lab` (= one AWS account), owned by an AWS Builder ID with MFA | activate advanced features; new account with "Sign up for AWS (advanced)" | simplest secure setup: no root user, no IAM user, no long-lived key; Organizations, Identity Center and the admin role are managed by AWS; every service of the three exercises is supported (EC2, VPC, S3, IAM, OpenSearch Service, Elastic Load Balancing). Activating advanced features is irreversible and requires the Paid plan first. Consequence: IAM users can only be used for programmatic access; region and service list are imposed |
| Region `eu-north-1` (Stockholm) | `eu-west-3` (Paris, first proposal); `us-east-1` (starter kit) | imposed by the project (chosen from the contact address); no impact on these exercises. Consequence: all exercises run in `eu-north-1` |
| CLI authentication with `aws login` (temporary credentials of `AccountFullAccessRole`, valid 12 h, renewable for 90 days) | IAM user access keys | no long-lived secret on the laptop. Consequence: Terraform must read the `login_session` profile (Terraform 1.15+ and AWS provider 6.23+, to be checked in the official changelog); fallback: `aws configure export-credentials --format env` |
| Cost guardrails: Free plan (no charge possible, until 2027-05-09, USD 100 credits) and an AWS Budgets alert | no alert | the Free plan caps the cost; the alert shows credits being consumed. Consequence: every session still ends with `terraform destroy` |

## State bootstrap (2026-11-11)

| Decision | Rejected | Reason |
|---|---|---|
| Terraform `~> 1.17` (1.17.1 installed), AWS provider `~> 6.72` (6.72.0, 2026-11-04); exact versions locked by the committed `.terraform.lock.hcl` | starter kit `~> 4.16`; no constraint | latest stable releases, checked on releases.hashicorp.com and the provider changelog; `~>` accepts fixes and features, not a new major version. Reading the `aws login` session needs Terraform 1.15+ (S3 backend) and provider 6.23+ |
| Files split as in the official style guide: `terraform.tf`, `providers.tf`, `backend.tf`, `main.tf`, `variables.tf`, `outputs.tf` | one `main.tf`; `versions.tf` | a reviewer knows where to look; this is HashiCorp's documented convention |
| `prevent_destroy` on the state bucket | no protection | every session ends with `terraform destroy`; run by habit in `00-bootstrap/`, it would delete the bucket holding every state. Consequence: deleting the bucket at the end of the project requires removing this line first |
| State bucket settings: versioning and the four S3 Block Public Access settings declared in code; encryption left to the S3 default (SSE-S3) | explicit `aws_s3_bucket_server_side_encryption_configuration`; SSE-KMS | versioning is the only setting S3 does not enable by default, and it allows rolling back a damaged state; public access is blocked by default but can be reopened, so AWS recommends the four settings on each bucket (Security Hub S3.8) and Terraform then detects a manual change; SSE-S3 applies to every object since 2023-01-05 and cannot be turned off, so declaring it adds nothing; SSE-KMS adds cost for no gain here |

## Exercise 1 layout (2026-11-11)

| Decision | Rejected | Reason |
|---|---|---|
| Docker variant of Ex1 removed (`terraform/docker/`, `ansible/hosts_docker`); `terraform/aws/` flattened into `terraform/` | keep both variants | the Docker option is not used (QEMU needs `/dev/kvm`); dead code makes a reviewer wonder which variant is the real one; the files stay in the starter kit commit. The Docker variants of Ex2 and Ex3 are decided in their own branches |
| Kit `main.tf` removed at piece 3a, rewritten at 3b (instance, security group, key pair) | keep it while adding `terraform.tf` and `providers.tf` | its `terraform {}` and `provider "aws"` blocks would duplicate the new ones, and its `tls`/`local` resources would add two unused providers to the lock file. The original stays in the starter kit commit |
| Backend values written in the code, account ID included (`devops-iac-aws-lab-tfstate-271802700738`) | partial configuration (`-backend-config=backend.hcl`, git-ignored) | a backend block cannot read variables; AWS does not treat an account ID as a secret (it grants nothing without credentials); a reviewer sees where the state lives. Consequence: the account ID is public on GitHub; in a company, the repository would be private |
| Each block is preceded by one or two lines saying what it is and what it is for here, followed by the link to its official doc page | the registry's one-line description ("Provides a security group resource"), which names the block without explaining it; no links | someone who has never seen a security group understands its role; the code can be checked against its source in one click. Consequence: links to update if HashiCorp moves its pages |
| Security group rules as separate `aws_vpc_security_group_ingress_rule` / `egress_rule` resources; outbound allow-all declared explicitly | inline `ingress {}` / `egress {}` blocks (starter kit) | the provider docs call separate rules the current best practice; inline blocks conflict with them. Terraform removes the AWS default egress rule, and apt needs outbound access |
| SSH (22) open to the admin IP only; HTTP (80) open to anywhere | SSH from `0.0.0.0/0` (starter kit); HTTP restricted to the admin IP | least privilege for administration; port 80 is the web server's purpose, and the starter kit did not open it at all (step 7 would fail) |
| Admin IP in a variable, its value in a git-ignored `terraform.tfvars` | IP written in the code | a personal IP does not belong in a public repository (unlike the account ID, it identifies a person). Consequence: when the home IP changes, update one line; a reviewer without the file is prompted for the value at plan |
| Ubuntu 26.04 LTS, latest image looked up by `aws_ami` with `owners = ["099720109477"]` (Canonical's AWS account) | Ubuntu 24.04 LTS; AMI ID hard-coded (starter kit) | latest LTS (supported until 2031), handled by ansible-core 2.20; the owner filter guarantees the image comes from Canonical, not from anyone publishing an image with the same name. Consequence: when Canonical publishes a newer image, plan shows the instance replaced; accepted because every session ends with destroy (fix if needed: `ignore_changes = [ami]`) |
| `t3.micro` in the default VPC, no `associate_public_ip_address`, no `metadata_options` | `t2.micro` (starter kit); explicit settings | `t3.micro` is Free plan eligible in `eu-north-1` (checked with `describe-instance-types`); default subnets already assign a public IP; the AMI already enforces IMDSv2 (`ImdsSupport v2.0`) |
| Exercise 1 delivered in two pull requests: Terraform (with the bootstrap), then Ansible on a new branch | one pull request at the end of the exercise (initial plan) | the Terraform part is complete on its own (the server answers over SSH); a smaller pull request is easier to review; merge before opening the next branch |

## Ansible (2026-11-13)

| Decision | Rejected | Reason |
|---|---|---|
| ansible-core `2.21.6`, installed with pipx and pinned (`pipx install --force "ansible-core==2.21.6"`) | `2.20.4` (installed); `2.22.0` (latest on PyPI, 2026-11-02) | 2.20 stopped receiving security fixes on 2026-11-02; 2.21 gets them until May 2027 and supports Python 3.9 to 3.14 on the managed node (official support matrix); 2.22.0 is a fresh `.0` release whose managed-node Python support is not yet documented. Consequence: Python on the Ubuntu 26.04 instance must be 3.14 or older (checked at the first `ping`) |
| Static inventory `ansible/hosts` (starter kit `hosts_aws` renamed, as in the brief): one host aliased `my-vm`, with `ansible_host`, `ansible_user=ubuntu`, `ansible_ssh_private_key_file`; no group | kit line (`ansible_ssh_user`, the old parameter name, and no key); a `[web]` group; dynamic inventory | the brief expects `my-vm \| SUCCESS`; the key must be named because it is not the default one; `all` already covers a single host |
| Instance public IP committed in `hosts`, copied by hand from `terraform output public_ip` after each apply | IP kept out of git; `hosts` written by Terraform (`local_file`) | the IP belongs to AWS and is released at destroy, so it identifies no one (unlike the admin IP in `terraform.tfvars`); `hosts` is a deliverable the reviewer must read. Consequence: the committed IP is stale after destroy and one line changes at each apply (fix: a `local_file` resource, about 10 lines) |
| Python interpreter set in the inventory: `ansible_python_interpreter=/usr/bin/python3` | default discovery (`auto`, warns); `auto_silent`; `/usr/bin/python3.14` | `auto` guessed `/usr/bin/python3.14` and warned the guess could change; `auto_silent` only hides the warning; `/usr/bin/python3` is Ubuntu's system Python and follows distribution upgrades, unlike a versioned path |
| App files copied with `ansible.builtin.copy` | `ansible.posix.synchronize` (rsync) | `copy` ships with ansible-core; `synchronize` needs the extra `ansible.posix` collection. About ten files: speed does not matter, and `copy` compares checksums, so a rerun copies nothing |
| nginx site in `/etc/nginx/conf.d/app.conf`; Ubuntu's `sites-enabled/default` removed | Debian layout (`sites-available/app.conf` + link in `sites-enabled/`) | the Ubuntu `nginx.conf` already reads `conf.d/*.conf`; one site needs no enable/disable switch, so no link task. The default site must go anyway: it also declares `listen 80 default_server`, and nginx refuses two default servers on the same port |
| Starter kit `app.conf` fixed: `json` out of the one-year cache, redundant `Cache-Control "public"` removed on HTML, `/50x.html` error page removed | kit file unchanged | `olympic.json` has no fingerprint in its name; on HTML, `Cache-Control "public"` only added noise next to the `no-cache` sent by `expires -1y`; Ubuntu's nginx package has no `/usr/share/nginx/html/50x.html` (checked) |

## Exercise 2: ELK stack (2026-11-13)

| Decision | Rejected | Reason |
|---|---|---|
| ELK run locally with Docker Compose (exception to "AWS for the three exercises") | starter kit AWS option | import and dashboard steps are identical in both options, only the start differs; locally, Elasticsearch can be queried directly (`curl localhost:9200`) to see the index and the ingest pipeline; the kit `main.tf` creates an `Elasticsearch_7.10` domain served with Kibana OSS, which most likely lacks the file upload the brief requires, and it uses static AWS keys, `us-east-1` and no access policy; no AWS wait, cost or destroy. Consequence: no managed service experience in this exercise; switching back is cheap, as the brief allows |
| Elasticsearch and Kibana `7.17.29` (latest 7.x, arm64 images checked with `docker manifest inspect`) | `7.14.0` (starter kit); `9.x` (current, 9.6) | 7.14 ships a log4j version affected by Log4Shell (fixed in 7.16.2); 7.17 keeps the same UI and settings; 8.x and later enable security by default (passwords, TLS, Kibana enrollment token), about an hour of setup unrelated to the deliverable |
| Ports published on `127.0.0.1` only; transport port 9300 not published | `9200:9200`, `9300:9300`, `5601:5601` on all interfaces (starter kit) | security is off (`xpack.security.enabled=false`), so anyone on the same network could read or delete data; Elastic's own 7.17 Docker examples bind to `127.0.0.1`; 9300 is node-to-node traffic, useless with a single node |
| Kibana pointed at Elasticsearch with `ELASTICSEARCH_HOSTS` | `ELASTICSEARCH_URL` (starter kit) | `ELASTICSEARCH_URL` is the 6.x name, ignored by Kibana 7; the kit only worked because the default value is the same URL |
| Index `nginx-access` created with `"number_of_replicas": 0` | default (1 replica) | Elasticsearch never puts a replica on the same node as its primary; with one node the replica stays unassigned and the cluster turns yellow. A replica protects nothing on a single node |
| Kibana `histogram:maxBars` raised from 100 to 200 | 1-day bars; a shorter time range | the brief asks for 12-hour buckets: 59 days make 118 bars, over the default limit, and Kibana silently widens the interval to one day. Consequence: a manual step in the README, since advanced settings are not part of the dashboard export |
| Brief read as: "cumulated data per 12 h" = sum of `bytes` per 12-hour bucket; "cumulated top 5" = stacked bars of the 5 most requested URLs over the whole period, without an "Other" group | running total of bytes; top 5 computed per bucket | the brief says the histogram "helps identify periods of high activity", which a running total cannot show; "Other" would hide the top 5 under every other URL |
| Dashboard exported as NDJSON (`kibana/`) and committed with the four screenshots | screenshots only | the export makes the dashboard reproducible and its settings readable; it holds no secret (checked: index pattern and dashboard only) |
| Log analysis (`analysis.md`) run with an AI assistant, disclosed as such; every finding given with a KQL query to replay in Kibana, and every figure cross-checked on the raw file | no analysis (not required); analysis presented without its method | the exercise is about observability, so reading the logs gives it a purpose; a reviewer can check each figure without the AI |
| Starter kit `aws/` option and `docker/README.md` removed; the Ex2 README covers the local run | keep both options and the kit README | same rule as Ex1: unused code makes a reviewer wonder which variant is real; the kit README announced an app on port 8000 that the compose file does not run. The originals stay in the starter kit commit |

## Exercise 3: load balancing (2026-11-14)

| Decision | Rejected | Reason |
|---|---|---|
| HAProxy run locally with Docker Compose (second exception to "AWS for the three exercises") | starter kit AWS option (3 EC2 instances) | the exercise is about HAProxy settings and health checks, not provisioning (shown in Ex1); in the kit AWS option `haproxy.cfg` is edited by hand over SSH on a VM destroyed after each session, so the deliverable would not live in git, and its `main.tf` repeats every flaw fixed in Ex1 (`us-east-1`, key generated into the state, SSH from `0.0.0.0/0`, provider `~> 4.16`); locally, a failure is simulated in seconds, which makes tuning the timeouts practical. Consequence: no real network between machines; the HAProxy part is identical |
| `haproxy:3.4` (latest LTS, 3.4.7, supported until 2031-Q2) and `nginxdemos/hello:0.4`, checked on haproxy.org and Docker Hub | `haproxy:2.3` and unpinned `nginxdemos/hello` (starter kit) | 2.3 has been unmaintained since 2022; pinned versions are reproducible. The image runs as a non-root user since 2.4, so `net.ipv4.ip_unprivileged_port_start=0` lets it bind port 80, as the image documentation shows |
| Only HAProxy published, on `127.0.0.1:8080`; config mounted read-only | `8080:80` on all interfaces | same rule as Ex2: reachable from the laptop only; the web servers are reached through HAProxy, never directly |
| HTTP health check: `GET /` must answer 200, `inter 2s fall 3 rise 2` | TCP check; `fall 1` | a TCP check only proves the port is open, not that nginx answers; one missed probe should not remove a healthy server (false alarm), and 3 failures still detect a real outage in about 8 s |
| `resolvers docker` (Docker embedded DNS, `127.0.0.11`) with `init-addr libc,none` | names resolved once at startup (default) | a restarted container may get a new IP address, and automatic recovery would then fail; `init-addr none` lets HAProxy start while a server is missing |
| `timeout connect 1s`, `retries 2`, `option redispatch` | starter kit `timeout connect 5s`, default retries, no redispatch | the first failover test showed requests sent to a stopped server hanging 10 to 15 s (5 s per attempt, retried on the same server) until it was marked down; on one Docker network a healthy server connects in under 1 ms, and redispatch sends the last attempt to the other server: about 1 s lost, no error (see `failover-test.log`) |
| No stats page; the HAProxy log (`failover-test.log`) is the proof of the failover test | stats page (screenshot) | the log shows, per request, which server answered and with what code, plus every `DOWN` / `UP` change, in a file a reviewer can read without running anything |
| Starter kit `aws/` option and `docker/README.md` removed; the Ex3 README covers the local run | keep both options and the kit README | same rule as Ex1 and Ex2; the kit README named the file `haproxy.conf`. The originals stay in the starter kit commit |
